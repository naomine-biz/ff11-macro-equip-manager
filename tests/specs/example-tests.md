# Example Test仕様

根拠: [要件](../../requirements.md)と[設計上の制約](../../docs/design-constraints.md)。
本書は正本から導いた検証仕様。正本との相違は[文書の管理](../../docs/README.md)の手順で解消する。記載ケースの実装・実行状況は別途確認する。

## 共通条件

- 全ケースは合成ファイル、一時ディレクトリ、固定辞書、偽プロセス一覧で実行する。実ゲーム・実レジストリ・実メモリ・ネットワークへのアクセスは拒否する。
- ケースの状態は独立させる。ゲームファイルへの書込回数、書込先、置換、バックアップ、作業保存、復旧イベントを記録する。
- `C1`、`C2`: 異なるキャラ。`B0`: 手持ち、`B1`: 金庫、`B8`: ワードローブ1、`B10`〜`B16`: ワードローブ2〜8。収納集合は`B0`〜`B16`。
- `I(C,B,P,T)`: キャラC、収納B、内部位置P、種類ID Tの所持品。位置は表示順から独立させる。
- `S(B,P,T)`: equip動作の装備枠。`X=1001`、`Y=1002`は合成辞書の別種類。Xの名前は`テスト装備`。
- 特記しない限り全17収納を読込済み、位置重複なし、数量不明、オーグメント取得不可。他の行・枠・持ち物は空。
- 空セットは16枠すべてkeep。マクロは名前と6行。空マクロは名前と全行が空。
- `W`: 作業値、`SAVED`: 保存済み値、`H`: 履歴、`K`: 履歴カーソル、`F`: ゲーム側の合成ファイル。
- `unchanged(F)`は全ファイルの存在・内容バイトが操作前と同一で、書込・置換・削除要求が0件。
- 表の期待結果はすべて必須。保留理由は対象を特定できること。実装の列挙名・文言の完全一致は要求しない。
- 将来機能のケースは実装前の受入仕様として保持する。未決定の振る舞いは末尾に列挙し、期待値を推定しない。
