## 目標の責務境界

| 担当 | 入力と出力 | 担当する処理 |
|---|---|---|
| ドメインモデル・判定 | 意味上の値と参照情報 → 妥当性・参照状態 | 値の制約、参照解析、候補判定。ファイル形式とUIへの依存を持たない |
| 編集操作 | 編集要求＋現在値 → 変更案または対象付きのエラー | マクロ名・行・装備枠・移動などの意図を解釈し、直接変更とカスケード変更を列挙する。I/Oなし |
| 編集セッション | 変更案 → working・履歴・cursor | 前提検証、一括適用、Undo／Redo、意味上のdirty。baselineとsavedを保持する |
| アプリケーションサービス | UIの要求 → プレビュー・適用結果・保存結果 | 操作群とセッション、作業ストア、保存計画器、書込み実行器を調整する。作業保存が成功してから内部状態を更新する |
| 保存計画器 | saved・working・保存範囲・読込資料 → 保存案と保留理由 | 意味上の差分、保存対応範囲、参照依存グループを決め、エンコーダーへ変換を依頼する。プレビューでは書き込まない |
| ファイルアダプター | 原本・変更値 → 置換バイト／検証済み結果 | パス対応、デコード・エンコード、未知領域保持、ハッシュ、排他、バックアップ、置換、検証、復元 |
| 作業ストア | 編集セッション・版 → アプリ専用作業ファイル | 自動保存、別のアプリによる更新の検出、履歴復元、版管理。ゲーム保存用の実行器から分離する |
| UI | ユーザー入力・上記の結果 | 操作の入力、差分・警告・保留理由の表示、明示的な適用・保存の依頼 |

UIはアプリケーションサービスを呼び、サービスはドメインの判定、編集セッション、保存計画の処理を呼ぶ。ファイル・作業ストアの具体実装をサービスへ渡す。ドメインからGUI、Path、レジストリ、プロセス操作、バイナリオフセットを参照しない。純粋な判定関数のUIからの利用は許容するが、編集状態の更新はサービス経由に統一する。

クラス名やファイル構成は実装時に決める。責務を分ける単位には、クラスのほかにモジュールや関数も使える。

## 編集状態と変更案の構造

「意味上の値」は、マクロの名前・各行、装備枠の動作・種類ID・収納・位置など、ユーザーが編集する内容を指す。原本バイトや参照状態の再計算結果は、この比較に含めない。

- baseline: 履歴を再生する起点。保存によって書き換えない。
- working: 表示・参照判定・次の編集の対象。変更はセッションのapply・undo・redoで反映する。
- saved: 最後に保存成功を確認した意味上の状態と原本情報。部分保存時は保存した範囲だけ更新する。
- history/cursor: ユーザー操作を戻すための情報。保存対象はsavedとworkingの差分で決める。dirtyも同じ意味上の比較を使う。
- 読込資料: 原本バイト、ファイル指紋、位置対応、未解決トークン等。ファイルアダプターが保持・解釈する。現在のraw_hex等は移行期間中保持し、履歴互換性とバイト保持を確認してから分離する。
- 派生参照状態: workingの変更後に再評価する。装備セット枠の属性として利用を継続し、内容差分・履歴の前提判定からは分離する。

変更案は対象キー、変更前後の意味上の値、操作名、直接変更／依存更新の説明、前提条件を持つ。キーはインストール・キャラとマクロ座標またはセット番号を含む。既存の位置キーを維持し、移動は移動元・移動先・参照元への変更を一つの案にまとめる。上書き、入替え、空き位置への移動は操作として区別する。キャラ間コピーでは元と先を明示し、先キャラの持ち物参照を検証する。詳細なコピー・移動規則は当該機能の着手時に定義する。

保存案は意味上の変更一覧、保存可能な依存グループ、保留対象と理由、対象ファイルごとの原本／置換バイトと指紋、依存ファイル、デコード後の期待値を持つ。作成後の編集または読込元変更を検出したら案を無効化する。保存結果は検証済みの範囲・原本情報・バックアップ先・復旧状態を返す。

## 守る条件

1. **編集の一括性**: 一つの案の全前提を検証してから内部状態を更新する。一枠でも失敗したらworking・履歴・cursorをすべて維持する。カスケード変更も一回のUndo／Redoに含める。
2. **入力検証**: 対象キーの存在・重複、値の型、マクロの6行構造、枠の動作と参照値を検証する。汎用のChangeを受け取る処理でも同じ構造検証を行う。表示上の警告と編集を拒否するエラーを区別する。
3. **自動補正と手動選択**: 自動補正は一意な候補という既存条件を維持する。手動選択はユーザーが選んだ収納・位置・種類IDの妥当性を検証する。複数候補を自動で選ばない。オーグメントは一致条件に追加しない。
4. **履歴とdirty**: 操作後のUndoで意味上の元状態、Redoで編集後状態へ戻る。Undo後の新操作は後続Redoを破棄する。無変更の操作は履歴へ追加しない。保存後のUndoはworkingの変更として扱う。
5. **作業保存**: 作業ファイルの保存失敗では現在のセッションを維持する。復元は版・読込元・履歴の妥当性を検証する。外部更新や破損時は既存作業を保管し、暗黙に上書きしない。
6. **保存単位**: 一つのカスケード操作で生じた参照依存グループは全体を保存する。セット移動だけ保存し、参照マクロの更新を保留するような分割を禁止する。編集履歴は依存の由来を補助するが、最終差分と参照整合性から保存グループを構築する。
7. **部分保存の可視性**: 独立したグループの部分保存は許容する。保存される対象・残る対象・各理由をプレビューに示す。依存を安全に判定できない場合は関連範囲全体を保留する。未対応編集を黙って除外しない。
8. **形式上の保存可否**: 文字数とエンコード後のバイト上限を区別する。CP932変換不能、定型文の曖昧な逆変換、未対応バイナリはプレビューで対象付きのエラーとする。切詰め・代替文字で成功扱いにしない。定型文の編集に着手する前に、表示文字とトークンIDを対応付けて保持する方法を決める。
9. **原本保持と検証**: 未編集部分・未知領域を保持し、変更を許すバイト領域とチェックサムを限定する。置換バイトの全一致と再デコード後の意味上の期待値を検証する。
10. **競合と依存**: 書込み時にゲーム終了、対象と依存ファイルの指紋、プレビューの有効性を再確認する。依存は操作ごとに宣言する。名前変更のように持ち物に依存しない操作へ、全収納必須条件を一律に広げない。
11. **保存成功と復旧**: 全原本のバックアップと書込用ファイルの準備を終えてから置換する。OS上の置換は一ファイル単位。途中失敗は今回の出力に一致する対象を復元し、外部更新を保護する。部分保存・復元失敗は復旧待ちとして後続保存を止める。
12. **チェックポイント**: 検証済み保存結果を得てから保存済み状態を更新する。書込前のpending記録と、書込成功後の作業同期を維持する。作業同期だけ失敗した場合は保存完了と復旧待ちを区別し、再起動時にファイルと作業状態を照合して復旧する。

## 段階的な移行と完了条件

| 段階 | 実装範囲 | 完了条件 |
|---|---|---|
| 1 基盤の整理 | 意味上の値比較・変更案検証、編集操作を受け付けるメソッド、対象付き保留理由、共通書込み実行器 | 既存Fixの出力バイト・履歴・復元挙動を維持。UIからの直接変更を防ぐ境界テストが通る |
| 2 マクロ個別編集の保存 | 名前・6行を編集から保存まで通す。定型文表現とバイト上限の設計を確定 | 手編集とFixの混在、名前のみ／行のみ、上限超過、変換不能、未変更トークン保持を合成データで検証 |
| 3 装備セット個別編集 | 名前と各枠のkeep/remove/equip、候補を手動選択 | 自動一意判定と手動選択を区別。各動作のバイナリ変換とUndo／Redo、混在保存を検証 |
| 4 移動・コピー | パレット・マクロ・セット移動、キャラ間コピー、参照更新 | 衝突方針と参照更新範囲を先に定義。依存更新が一括Undo／保存され、未対応があればグループ全体を保留 |

各段階で仕様・ドメイン・UI・保存対応範囲を一緒に更新する。現行のFix保存は移行完了まで維持する。個別編集の追加に合わせて直接のファイル書込経路を増やさない。

## テストで確認する条件

現行のtest_editing.pyは一括Undo／Redo、古い前提での全体中止、作業保存失敗、履歴復元を扱う。test_macro_saving.pyとtest_equipment_saving.pyはバックアップ、競合、対象外バイト保持、途中失敗、チェックポイント復旧、保存後Undo／Redo、合成データのGUI保存を扱う。これらのテストは既存の補正機能を対象とする。追加機能の検証項目は次の段落に示す。

追加するテストでは、(a) ドメイン／編集操作のI/O・GUI非依存、(b) 不正な変更案の拒否と現在の編集状態が変わらないこと、(c) 依存グループの部分保存拒否、(d) 保留対象・理由の表示、(e) 操作別依存ファイル、(f) 文字列／定型文の往復変換、(g) 保存後の履歴再開と再編集、(h) 各失敗点での復旧状態を確認する。テストには合成ファイルと偽のストア／実行器を使い、実ゲームのパスを使わない。実機への保存検証はユーザーの明示的な依頼時に別途行う。


## 段階1の実装結果（2026-10-28）

- edit_values.pyに意味上の値比較と構造検証を分離。dirtyはキャラ・マクロ・セットのキー集合を含めて比較する。履歴の前提検証はraw_hexや派生参照状態から独立させた。
- EditSessionは汎用Changeでも型、位置キー、6行、16枠、変更する装備枠の動作・参照値を検証する。未変更の未知値は保持する。意味上の無変更は前提検証を通したうえで履歴に追加しない。Undoは検証済みの元状態へ戻せる。
- 装備セット補正案のEditへの変換を純粋なplan_equipment_editへ移動。個別編集はEditor.prepare_macro_editで受け付ける。
- Editorが編集セッションを管理する。session参照とsnapshot()は切り離したコピーを返す。UIはsnapshot()と軽量なedit_status()を使い、内部セッションへ直接アクセスしない。作業ファイルv2の形式と既存履歴の再開方式は維持する。
- save_plan.pyのDeferredChangeは対象と理由を保持する。deferred件数はその一覧から導出する。GUIプレビューに詳細を表示し、保留のみの場合もエラー表示に対象と理由を含める。対象の追加・欠落を保存計画作成時に検出する。
- file_transaction.execute_batchへ依存ファイルのロック、ハッシュ確認、全原本バックアップ、一時ファイル準備、置換、検証、失敗時復元を集約。各保存アダプターはパス・バイナリ・補正条件を検証するコールバックを渡す。バックアップの既存形式、復元CLI、書込バイトの生成方法は維持する。
- equipment_savingからmacro_savingへの依存を解消。UI境界、ドメインのI/O非依存、両保存経路が共通実行器を通ることをテストする。

通常テスト102件中96件成功、6件は明示有効化が必要な検証としてスキップ。うち合成データを使うGUI検証5件を別途実行して成功した。実ゲームを読む統合テストは実行していない。ゲームデータの読取・書込、アプリの再起動は本段階の実装検証で行わない。

後続段階: 定型文の識別を保持する任意テキスト編集のエンコード、手動の装備枠編集、依存グループを伴う移動・コピー、各保存処理に共通する戻り値の定義、原本情報をモデルから分離する移行。段階1で保存できる変更は、これまでと同じ自動補正に限る。保存計画を作る際に対象の追加・欠落を検出した場合は、処理を中止する。
